# Codex 全局开发规范

规范版本：1.1（2026-09-16）。

本文件定义所有 Git 仓库中的默认开发约定。仓库或子目录中的 `AGENTS.md`、`AGENTS.override.md` 以及用户当前任务的明确要求可以覆盖这里的通用规则。不得用全局规则覆盖项目已经确认的分支、测试、发布或安全流程。

## 核心原则

- 使用轻量 GitHub Flow：默认只长期保留 `main`，不主动引入 `develop`。
- 已有仓库优先遵循其真实默认分支、长期维护线和发布模型，不擅自把 `master` 改成 `main`、删除 `develop` 或迁移 Git 流程。
- `main` 始终代表已验证、可追溯的稳定代码；不得直接在 `main` 上开发普通需求。
- 一个明确任务对应一个短生命周期分支；一个分支只包含同一目标下的相关改动。
- 同一任务的后续修改复用尚未合并的原分支，不因每条消息重复建分支；已合并分支不承接新工作。
- 分支是工作空间，不是版本档案；生产版本通过从 `main` 创建的不可变 Git Tag 保存。
- 并行任务使用独立分支和独立 worktree；不得让多个任务在同一 checkout 中交叉写入。
- 保留用户已有改动，不覆盖、回滚、格式化、提交或删除无关文件。

## 分支模型与命名

默认分支格式为 `codex/<type>/<short-name>`，使用小写英文和连字符：

- 新功能：`codex/feat/<name>`
- Bug 修复：`codex/fix/<name>`
- 重构：`codex/refactor/<name>`
- 性能优化：`codex/perf/<name>`
- 文档：`codex/docs/<name>`
- 测试：`codex/test/<name>`
- 工程与依赖：`codex/chore/<name>`
- 紧急生产修复：`codex/hotfix/<name>`
- 发布候选：`codex/release-vX.Y.Z`

如果仓库已经规定其他命名方式，遵循仓库规则。分支名称表达任务目的，不使用 `final`、`new`、`latest`、`test2` 等含义不清的名称。

## 开始任务前

在修改任何文件前：

1. 阅读全局、仓库根目录和当前子目录生效的 `AGENTS.md` 或 override 文件。
2. 确认仓库根目录、当前分支、远端跟踪关系和 worktree：
   - `git status --short --branch`
   - `git branch --show-current`
   - `git worktree list`
3. 检查未提交改动并判断来源；无关改动不得纳入当前任务。
4. 识别真实默认分支、目标远程和上游关系；存在 fork、`upstream` 或维护分支时不得假定一定是 `origin/main`。
5. 安全时获取目标远程更新并记录基线 SHA。Fetch 失败或离线时不得声称代码已同步，只能在明确说明已知本地基线的前提下继续不依赖最新远端的工作。
6. 如果当前位于受保护分支且任务需要写入代码，先创建任务分支；不得先修改再补建分支。
7. 如果当前 checkout 有其他任务未提交改动，使用独立 worktree，不移动、自动 stash 或清理他人的改动。
8. 检查是否存在未完成的 merge、rebase、cherry-pick 或冲突；不擅自继续、撤销或覆盖其他任务的操作。

默认创建方式：

```bash
git fetch --prune origin
git switch --no-track -c codex/feat/example origin/main
```

并行开发时优先创建独立 worktree：

```bash
git worktree add <明确的安全路径> -b codex/feat/example origin/main
```

上例只适用于已经确认远程与默认分支的仓库，并且第二条命令只能在 fetch 成功后执行。不得让同一分支同时被多个 worktree 修改。

Codex 管理的 worktree 可能处于 detached HEAD；这不代表成果丢失。推送、交接或清理前应保护当前 HEAD、提交和未提交文件，再从当前成果建立可追踪分支。worktree 只隔离文件和 Git 状态，不自动隔离数据库、端口或外部服务。

## 开发过程

- 先确认任务范围和验收条件，再修改代码。
- 选择满足需求的最小实现，不借任务引入无关重构、依赖或基础设施。
- 修改前搜索相关实现、测试、契约和文档；不得只根据历史对话猜测当前状态。
- API、数据结构、业务口径、用户流程、配置或部署方式变化时，同步更新类型、测试和对应文档。
- 发现分支基线错误、来源不明的重叠改动或冲突时，停止写入并先厘清来源。
- 不使用 `git reset --hard`、`git checkout --` 或其他破坏性命令处理用户改动。
- 不使用未验证的模拟数据掩盖真实集成失败；生产不得静默回退到假数据。

## Commit 规范

默认采用 Conventional Commits：

- `feat: ...`
- `fix: ...`
- `refactor: ...`
- `perf: ...`
- `docs: ...`
- `test: ...`
- `chore: ...`
- `build: ...`
- `ci: ...`
- `release: ...`
- `merge: ...`

Commit 应当目标单一、逻辑完整且可审查。不要为了“提交小”把一个不可运行的中间状态拆成多个 Commit，也不要把多个无关任务塞进同一个 Commit。

提交前：

1. 检查 `git diff`、`git diff --stat` 和 `git diff --check`。
2. 运行仓库规定且与改动风险相称的测试、类型检查、Lint 和构建。
3. 只暂存当前任务的明确文件，不使用 `git add .` 吞入未知改动。
4. 确认不包含密码、Token、Cookie、私钥、真实个人数据、临时文件或构建产物。

普通“修改”或“修复”请求不自动授权 Commit、Push、创建 PR、合并、打 Tag、部署或删除远程分支。用户要求“提交”只授权本地提交；要求“推送”或“创建 PR”才授权推送本任务分支。合并、生产发布、Tag 和远程分支清理分别需要当前任务或仓库规则的对应授权，已经明确授权的同一范围不重复询问。

## 同步与冲突处理

- 发起 PR 或准备合并前，同步已确认的真实目标分支。
- 已推送或多人共享的分支默认通过合并目标分支更新，不擅自 rebase 或 force-push。
- 只有确认分支未共享且用户或仓库流程允许时才 rebase。
- 必须覆盖已发布任务分支时只在明确授权后使用限定目标的 `--force-with-lease`；禁止普通 `--force`，禁止重写受保护长期分支。
- 解决冲突时理解双方意图，保留两边有效改动；不得通过整文件覆盖来“消除”冲突。
- 合并后重新运行受影响验证，不能只依据冲突标记消失判断成功。

## PR 与合并规范

PR 或合并前必须满足：

- 改动范围清晰，没有无关文件。
- 相关测试、类型检查、Lint 和构建通过。
- 用户可见行为、接口、配置、迁移和发布影响已更新文档或 CHANGELOG。
- 已检查加载、空数据、错误、权限、兼容性和降级等与任务相关的状态。
- PR 说明包含目标、主要改动、验证证据、风险、已知限制和回滚方式。
- Codex 自检和 AI Review 不替代仓库要求的人工审查；真正禁止直推、强推和绕过检查应由托管平台分支保护、CI 与权限落实。

默认通过 PR 合入 `main`。是否使用 squash、merge commit 或 rebase merge，以仓库现有约定为准。没有约定时，短期单任务分支优先 squash；需要保留多分支整合关系的发布候选使用 merge commit。

不得因为“代码已完成”自动合并 `main`。合并生产分支属于单独授权动作。

## 发布准备与正式发布

区分两种模式：

### 发布准备

当用户说“提交”“推送”“准备发布”“准备部署”或含义相近但没有明确要求生产上线时：

- 完成相关验证、文档、版本和 CHANGELOG 检查。
- 提交并推送开发或候选分支。
- 不合并 `main`、不创建 Tag、不部署生产。
- 报告候选分支、Commit、验证结果和剩余步骤。

### 正式发布

只有用户在当前任务明确要求“合并 main”“打 Tag”“正式发布”“发布生产”“生产上线”或同等明确指令时：

1. 汇总本次发布范围，确认所有目标特性分支均已进入候选分支。
2. 更新 CHANGELOG、版本号、契约和发布文档。
3. 运行仓库要求的完整发布门禁。
4. 将候选分支合入 `main` 并推送 `main`。
5. 从 `main` 中已推送、已验证的 Commit 创建 `vX.Y.Z` Tag 并推送。
6. 只部署该不可变 Tag，不部署未提交工作区、开发分支或浮动的 `main`。
7. 验证应用版本、Commit、构建时间、健康状态、关键业务路径、数据库和上游契约。
8. 失败时停止后续动作，保留证据并按仓库流程回滚到上一稳定 Tag。

正式 Tag 优先使用 annotated tag；项目要求签名时使用签名 Tag。只推送本次授权的具体 Tag，不使用无差别 `git push --tags`。已经发布的 Tag 不移动、不覆盖，修复使用新版本号。

默认语义化版本：

- Patch：向后兼容的 Bug、配置、安全或小范围展示修复。
- Minor：向后兼容的新功能、行为、路由、评分或报告变化。
- Major：破坏性 API、运行时或数据迁移；必须单独确认迁移与回滚方案。

Tag 必须在部署前创建。正确顺序是：`merge main → push main → tag → push tag → deploy tag → verify`。

## 分支清理

特性、修复、重构、性能、文档、测试和 hotfix 通常是短期分支。直接通过 PR 合入目标主干的普通任务分支，在确认合并、无人使用且依赖解除后可以清理，不必机械等待下一次生产发布；只进入发布候选、尚未进入主干的特性分支继续保留。release 分支在准确 Tag、部署和生产验证完成后清理，仍承担补丁支持的 release/support 分支保留到维护周期结束。

删除前必须同时确认：

1. PR/MR 实际状态是 merged 且目标分支正确；closed、远端引用消失或长期未更新不代表已合并。
2. 分支尖端没有合并后新增、未被接收的工作。
3. 普通保留祖先关系的合并可用提交可达性辅助核验；Squash/Rebase 合并必须结合平台合并记录、合并时源 SHA 和最终结果判断，不能只依赖祖先关系。
4. 分支没有未提交、未推送或仍需继续修复的内容。
5. 分支没有被活跃 worktree、开放 PR、依赖 PR、流水线、自动化或其他人员继续使用。
6. 删除目标明确，不使用模糊变量、通配符或批量猜测。

建议核验：

```bash
git fetch --prune origin
git branch -r --merged origin/main
git merge-base --is-ancestor origin/codex/feat/example origin/main
git worktree list
```

正式发布授权本身不自动包含远程分支删除。用户明确要求“发布并清理分支”后，生产验证成功时可以删除本次发布已经合并的精确任务分支和 release 分支；不得顺带删除其他分支。其他场景只报告可清理列表。

删除顺序：先确认并安全移除不再需要的 worktree，再删除远端分支，最后删除本地分支。只使用安全删除 `git branch -d`；Squash/Rebase 后 `-d` 失败不等于成果未被接收，但也不得自动升级为 `-D`，强制删除需要明确证据和单独授权。

永久保留：

- `main`
- 仓库明确规定的其他长期保护分支
- 发布 Tag

## Hotfix

- 先确认真实生产 Commit、Tag 和影响范围。只有 `main` 与生产基线一致时才从 `main` 创建；如果 `main` 已包含尚未上线的功能，从实际生产 Tag/Commit 或指定维护线创建 `codex/hotfix/<name>`。
- 只包含恢复生产所需的最小修复。
- 运行完整相关门禁，合入 `main` 后创建新的 Patch Tag。
- 通过独立 PR 将修复回灌 `main` 及仍需该修复的维护线，避免后续版本回退。
- 生产验证成功后按普通短期分支规则清理。

## 新项目规范初始化

- 新建或首次接入 Git 项目时，检查仓库根目录是否已有 `AGENTS.md`。只读任务不修改仓库；用户授权开发或初始化时，缺少项目规则的仓库应先从 `~/.codex/project-standards/templates/` 建立项目规则，再开始普通开发。
- 使用 `~/.codex/bin/codex-project-standard init <仓库路径>` 初始化新仓库。该命令不得覆盖已有 `AGENTS.md`，已有项目必须人工合并并保留真实技术栈、测试、分支和发布规则。
- 项目 `AGENTS.md` 只补充仓库真实差异，但必须明确默认/集成分支、任务分支基线、验证命令、版本来源、Tag、部署入口、生产验证和回滚方式；未知项必须标记待确认，不得猜测。
- 初始化后运行 `~/.codex/bin/codex-project-standard check <仓库路径>`。存在占位符、缺少规范版本或缺少必填章节时，不得声称规范已完成。
- 团队共享的关键约束必须提交到仓库，不能只依赖某台机器的全局规则。托管平台仍应配置分支保护、必需 CI 和审查规则。
- `AGENTS.override.md` 只用于明确的临时或目录级覆盖，不作为共享主规范；覆盖结束后按正常任务流程移除或还原。

## 完成报告

每次开发或发布任务结束时，明确报告：

- 当前分支和最终 Commit。
- 修改范围与未包含的无关改动。
- 已运行的验证及结果。
- 文档、版本和 CHANGELOG 是否更新。
- 当前状态属于仅本地修改、已提交、已推送、已合并 `main`、已打 Tag 或已部署生产中的哪一级。
- 尚未完成的风险、人工验收和下一步。
- 已删除的分支，以及因为未满足条件而保留的分支。
