# Project instructions

这是个人投研决策看板，当前处于已有生产环境的 V1 持续开发阶段。前端采用 Vue 3、TypeScript 和 Vite，后端采用 FastAPI 与 PostgreSQL；在现有需求证明需要前，保持模块化单体，不拆分微服务。

## Source of truth and scope

- 已确认产品需求以 `docs/product/` 为产品依据；已接受的重要技术决策以 `docs/adr/` 为依据；当前接口与集成状态记录在 `docs/technical/`。
- 代码和测试用于核验当前实现，不得用现有实现反向覆盖已确认需求。文档与实现冲突时，明确指出差异，并按当前任务中确认的方向同步更新。
- 历史对话只作为线索，不自动视为长期有效的需求、发布授权或技术决策；需要持续生效的结论应写回产品文档或 ADR。
- 未确认的能力标为“待验证”或“暂不考虑”，不得借修复、重构或原型制作擅自扩大 V1 范围。
- 不在本文件重复易过期的具体版本号、地址和供应商状态；从代码、发布元数据和技术文档读取当前值。

## Product and data safety

- 本地开发、测试和尚未接入的功能可以使用明确标记的模拟数据；生产环境不得静默回退到模拟数据或用补造字段伪装真实结果。
- 上游失败时保留最后一份健康快照，并明确展示 `stale`、`unavailable`、部分失败或“证据不足”；不得清空有效历史或产生伪精确结论。
- 区分事实数据、第三方观点、模型推断和用户判断。确定性指标、排名、阈值与规则判断由可验证程序生成，AI 只基于可追溯证据整合和解释。
- 数据和页面至少保留可用的数据来源、业务时间、实际交易日、更新时间、时区、质量状态、契约版本和规则/映射版本。
- 不实现自动交易，不承诺投资收益；不接入券商、真实持仓、成本、仓位或资金账户，除非用户在当前任务中单独确认范围和安全边界。

## Trading-date semantics

- 日期筛选输入表示“观察日期”。系统按目标市场的交易日历，解析到不晚于观察日期的最近可用交易日或快照；不得使用未来数据，也不得把自然日伪装成交易日。
- 页面同时展示观察日期与实际数据交易日；发生周末、休市、数据延迟或历史回退时，明确说明回退原因和快照生成时间。
- 同一交易日存在多份快照时，默认读取当日最新的有效版本；历史查询不得触发重新抓取、覆盖或改写既有快照，除非任务明确要求回补或迁移。

## Integration boundary

- `stock-analyzer` 是股票主数据、行情、量化规则结果和美股观察数据的上游；`marketNewsFeed` 是投研信息上游。Dashboard 负责展示、关联、研究状态、决策与复盘。
- 上游数据只通过稳定、鉴权、版本化、可追溯的 API、Webhook 或适配层接入，不直接读取上游数据库或依赖其内部表字段。
- 自选股新增、暂停和恢复属于明确授权、可审计的窄范围命令；除这些已确认命令外，Dashboard 默认不反向修改上游数据。
- `contract_version` 用于判断结构兼容性，`rules_version` 或映射版本用于标识业务逻辑，两者必须分开校验、存储和展示。结构不兼容时明确失败，不偷偷吞字段或伪造兼容结果。
- 第三方 API、模型、MCP 和 Skill 的许可、成本、隐私与稳定性需单独验证；真实凭证只在服务端或部署环境注入。
- 跨仓库修改前先读取目标仓库自己的 `AGENTS.md`。只在当前任务确实需要时修改上游，并分别完成测试、状态检查和提交，避免跨仓库改动混为一个提交。

## Workspace and implementation rules

- 选择满足当前需求的最小方案，避免无需求支撑的依赖、抽象、通用平台和基础设施。
- 开始修改前检查当前分支与 `git status --short`。保留用户和其他任务已有改动，不覆盖、回滚、格式化或提交无关文件。
- 同一 checkout 中如果另一任务正在写入，不编辑重叠文件；需要并行开发时使用独立 worktree。遇到来源不明且与本任务重叠的改动，先停止写入并说明冲突。
- 不使用 `git reset --hard`、`git checkout --` 等破坏性命令清理他人修改。每个提交只包含当前任务文件。
- 修改现有契约、业务口径或用户流程时，同步更新相应产品文档、技术文档、类型定义和回归测试。

## Secrets and production access

- 密码、Token、Cookie、Webhook、私钥、账户信息和真实个人投资数据不得出现在代码、命令参数、聊天内容、日志、截图、测试夹具、演示数据或仓库历史中。
- 只通过已配置的 SSH Key、未跟踪环境文件、系统钥匙串或部署密钥管理机制使用凭证；不得把明文秘密插入 `expect`、远程命令、URL 或可记录的 shell 历史。
- 读取日志或配置时避免输出秘密值，只验证是否已配置。发现秘密暴露时停止继续使用该凭证，明确报告暴露范围并建议立即轮换。

## Verification

- 前端变更至少运行受影响的非 UI 单元与逻辑 Vitest；页面或类型变更运行 `npm run build`。
- UI 不新增或运行组件 DOM、浏览器端到端（E2E）、Playwright、截图回归或像素级视觉自动化测试，也不把 UI 自动化验收作为完成或发布门禁。
- 后端变更至少运行受影响的 pytest；Python 代码运行 Ruff 检查，并执行 `git diff --check`。
- 页面变更的自动验证限于非 UI 逻辑测试、类型检查和生产构建；登录、交互、布局、视觉效果以及加载、空数据、错误、陈旧数据、权限和日期回退等界面状态由用户人工验收，Codex 不主动启动浏览器自动化。
- 集成变更同时验证正常响应、超时、鉴权失败、结构不兼容、部分数据缺失和最后健康快照降级路径。
- 跨模块契约修改或发布前，运行双方相关测试和契约检查；不能只以单个页面可见作为完成依据。

## Git and release policy

### Branch lifecycle and task isolation

- 本仓库采用 `main + 短期任务分支 + PR + 发布 Tag`，不引入长期 `develop`。`main` 是稳定主线，但生产实际版本以部署记录中的 Tag、Commit 和构建元数据为准。
- 普通任务分支使用 `codex/<type>/<short-name>`，`type` 取 `feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`chore` 或 `hotfix`；发布候选使用 `codex/release-vX.Y.Z`。名称使用小写英文和连字符，不编造任务编号。
- 一个独立任务对应一个短期分支。同一未合并任务的后续修改复用原分支，不因每条消息重复建分支；已经合并的分支不承接新工作。
- 新任务从已确认并更新的目标基线创建。默认基线是 `origin/main`，但执行前仍需确认远端、默认分支、分叉状态和基线 SHA；fetch 失败时不得声称已同步最新代码。
- 不必先切换本地 `main` 才能创建任务分支；工作区安全且 fetch 成功后可使用 `git switch --no-track -c codex/<type>/<name> origin/main`。禁止用 `switch -C`、`checkout -B` 重置已有同名分支。
- 并行任务使用独立分支和 worktree。同一分支不同时检出到多个 worktree；worktree 只隔离文件与 Git 状态，不自动隔离数据库、端口和上游服务。
- Codex 管理的 worktree 可能处于 detached HEAD。交接、推送或清理前先保护当前 HEAD、提交、未提交和未跟踪成果，再从当前成果建立可追踪分支；不得为恢复分支名称而重置回 `main`。

### Authorization and release modes

- 默认只修改代码和文档并完成验证；“修改”或“修复”本身不授权提交、推送、合并、打标签或部署生产。
- 用户只要求“提交”时，只提交当前任务相关文件，不自动推送；要求“推送”“创建 PR”或“准备发布”时，可完成必要的本任务提交并推送当前开发分支，但不合并 `main`、不打标签、不部署生产。
- 只有用户在当前任务中明确要求“正式发布”“生产发布”“发布生产”“上线”“生产上线”或“立即发布”时，才进入完整生产发布模式。单独的“发布”、`release` 或 `deploy` 表述不明确时，默认只做发布准备，并说明生产尚未执行。
- 合并、生产发布、Tag 创建/推送和远程分支删除是不同授权。正式发布授权不自动包含删除远程分支；只有用户明确要求“发布并清理分支”或单独授权清理时才删除指定分支。
- 发布授权只适用于当前任务明确的仓库、变更和环境；历史对话中的授权、其他仓库的发布请求或一次成功发布不得沿用。

### Version and tag rules

- 根目录 `VERSION` 是 Dashboard 应用版本的唯一发布来源；前端和后端必须读取该值。发布时 `package.json`、`package-lock.json`、`pyproject.toml`、API 版本信息、构建元数据和页面展示必须与其一致。
- 沿用现有 `vX.Y.Z` Git Tag 格式，Tag 必须与 `VERSION` 完全一致；同一版本不得对应多个内容不同且无法区分的部署产物。
- 向后兼容的问题、配置或安全修复增加补丁版本；向后兼容的功能、行为、评分、路由或报告变化增加次版本；破坏性 API、运行时或数据库变化必须由用户单独确认版本和迁移方案，不自动决定主版本升级。
- 上游服务、数据契约、量化规则、映射、模型和提示词使用各自版本，不随 Dashboard 应用版本自动递增；发布记录应列出最低兼容契约与实际规则版本。

### Production release gates

- 生产发布只使用从 `origin/main` 可达的不可变 Tag；不得直接部署未提交工作区、开发分支、仅存在本地的 Commit 或浮动的 `main`。工作区包含无关修改时，从干净的临时 release worktree 完成合并、验证和打标签。
- 发布 Commit 必须通过完整 CI。无法读取远端 CI 状态时，在本地运行与 `.github/workflows/ci.yml` 等价的完整检查，并明确报告没有核验远端 CI。
- 发布前确认需求、ADR、技术文档、追踪矩阵和 `CHANGELOG.md` 已按影响更新，且 `git diff --check`、Ruff、pytest、Vitest、前端构建和 Alembic 检查通过。
- 生产配置必须在不输出秘密值的前提下确认：`SEED_DEMO_DATA=false`、认证已开启、必需密钥已配置且不进入前端构建。个人密码登录部署允许长期使用 HTTP 和 `AUTH_COOKIE_SECURE=false`，不得因此阻断发布；使用 HTTPS 时设置 `AUTH_COOKIE_SECURE=true`，启用飞书 OAuth 时仍必须使用 HTTPS。
- 涉及数据库迁移时，先创建并验证可读备份，再检查和执行向后兼容的 Alembic migration；迁移失败立即停止。未经验证且可能丢失新数据时，不自动执行 downgrade。
- 涉及上游或契约变更时，先验证结构兼容性、鉴权、超时和降级路径。多仓库发布只在任务确实包含多个仓库时执行，并遵循“上游发布与契约验证成功 → Dashboard 发布”的顺序。
- 完整发布必须在干净发布状态下完成版本更新、发布提交、合并 `main`、推送 `main`、创建并推送 Tag，然后只通过仓库既有受限入口 `./deploy.sh <tag>` 部署；不得把密码写入 SSH、`expect` 或其他命令绕过部署器。

### Production verification and failure handling

- 部署后验证 `/api/v1/health`、`/api/v1/data-status`、`/api/v1/system/version` 和本次影响的 API 路径，并检查容器状态、错误日志、数据库连接与上游同步状态；登录、页面交互、布局和视觉效果列为用户人工验收项，不运行 UI 自动化。
- `/api/v1/system/version` 返回的应用版本、Commit、构建时间和环境必须与目标 Tag 的发布记录一致；仅有 HTTP 200 不足以判定发布成功。
- 发布开始前记录上一稳定 Tag 和数据库恢复点。生产验证失败时停止后续步骤，优先回滚应用到上一稳定 Tag；数据污染先暂停同步并保留审计证据，数据库只按已验证且无数据丢失的方案恢复。
- 发布结果必须记录并报告：应用版本、Commit、Tag、发布环境与时间、数据库迁移、上游契约、验证证据、已知限制和回滚点，并明确区分“发布准备完成”和“生产部署成功”。
- 多个小改动合并验证后集中发版，避免为单个非紧急问题频繁发布。详细执行步骤以 `docs/technical/deployment-operations.md` 为准；本文件只保存长期稳定的授权和门禁。

### Merge evidence and branch cleanup

- 直接通过 PR 合入 `main` 的普通任务分支，在确认 PR 已合并、没有新增独有成果、无人继续使用且依赖解除后可以清理；不必机械等待下一次生产发布。
- 只合入发布候选、尚未进入 `main` 的特性分支继续保留。release 分支在目标 Tag、部署和生产验证成功后清理；仍承担补丁支持的 release/support 分支保留到维护周期结束。
- 清理前核对实际 PR 状态、目标分支、合并时的源 SHA、分支尖端新增提交、未提交/未跟踪文件、关联 worktree、依赖 PR、流水线和其他使用者。closed、长期未更新或远程引用消失都不等于 merged。
- 普通保留祖先关系的合并可用 `git merge-base --is-ancestor` 和 `git branch --merged` 辅助核验。Squash/Rebase 合并后这些命令可能无法识别已经接收的成果，必须结合平台合并记录和最终 diff 判断。
- `git branch -d` 失败时先报告原因，不自动升级为 `git branch -D`。强制本地删除、远程分支删除、放弃未合并成果和强制移除 worktree 都需要明确目标、证据及对应授权。
- 获得清理授权后，先安全结束并移除不再使用的 worktree，再删除精确的远程分支，最后删除本地分支并刷新远程跟踪引用；不得用通配符顺带批量清理其他任务。

## Documentation

- 需求变化标明“已确认”“待验证”或“暂不考虑”，并检查文档链接、项目名称、术语、版本和实现状态的一致性。
- 已接受 ADR 不直接改写结论；方向变化时新增 ADR，并明确替代或废弃关系。
- 产品或技术状态发生实质变化时，在同一任务中更新对应文档，避免继续保留“尚未接入”“尚未部署”等过期描述。

## Completion

- 说明本次实现或确认的内容、涉及的数据与契约口径、验证结果和仍然存在的开放问题。
- 明确区分“仅本地修改”“已提交”“已推送”“已打标签”和“已部署生产”，不得用“完成”模糊替代实际发布状态。
- 若任务涉及生产数据或集成，报告实际数据日期、质量状态、版本与最后成功时间；不得仅报告接口返回成功。
