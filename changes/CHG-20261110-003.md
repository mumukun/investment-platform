# Change: CHG-20261110-003

## Title / Status

波段已买入交易跨规则持续跟踪与结算 / RELEASED（REL-20261110-002）

## Description

用户要求所有已经模拟买入的交易持续显示、跟踪并按入账时的约定结算。后续选股规则升级只作用于新信号。以真实入账记录为事实来源，原买入价格固定，历史评估、结算与胜率查询不依赖当前启用的选股规则。技术上的结果保存方式服务于该业务目标。

### 已核实问题与证据

本聊天于 2026-11-10 对生产进行了只读核查，运行版本 stock-analyzer 6.12.2、Dashboard 2.12.2，当前选股规则 v5.4.0。

- 波段买入账本按规则保留 v5.2.0 的 222 笔、v5.3.1 的 283 笔、v5.4.0 的 44 笔，共 549 笔。其中 11 月 9 日 43 笔、11 月 10 日 44 笔均存在，原始买入价和评分可读。这是检查时点的数量，实施对账使用当时实际总数。
- `swing_tracking.read` 用单一 rules_version 过滤交易，并逐笔从基础行情重算，未优先读取已保存结算结果。
- `scripts/swing_data_maintenance.py`、`swing_runtime.run_daily_scan` 和 `scripts/backfill_swing_outcomes.py` 的正常结算调用使用当前规则；后者只额外处理旧 v5.1.0 信号账本，没有覆盖全部已入账规则。
- 17:06 的旧版 v5.3.1 只读复算已有 22 笔可结算，其中 12 笔五日盈利；库内当时仅 1 笔标为 settled。查询可算与后台落账存在差距。
- Dashboard 的跟踪、完整历史和汇总将当前统计的 rules_version 继续传入查询，导致旧版已买入交易不可见。
- 候选历史与交易历史存在不同语义。11 月 9 日晚间的新规则候选更新了当天默认候选展示；原交易账本仍独立存在。本 Change 的交付对象为交易生命周期与交易历史。

### 1. 交易事实与结算约定

复用 `swing_simulated_trade`，一行代表一笔已经发生的模拟买入，trade_id 为查询、更新与去重身份。更早 `swing_signal_outcome` 中具有有效 entry_price、entry_time、entry_source 且 untradeable=false 的已成交参考记录，也纳入交易查询与原政策结算，使用带来源前缀的 event_id，避免与正式账本重复身份。

- 固定入账日期、入账价格、代码、当时名称、主导路径、评分、买入理由、原选股规则和计价依据。所有后续收益均以原 entry_price 为成本基准。
- 另存交易的结算约定 `settlement_policy`，包含独立政策标识、持有期、交易日口径、价格调整方式、费用口径和胜负定义。新交易写入时必须同时具备这些信息。
- 当前正式账本沿用五个后续交易日及原有同口径复权计算。T0 为买入日，T+1—T+5 各日均相对固定买入基准计算，T+5 大于 0 为盈利，等于 0 为持平，费用沿用现有未扣费口径。
- 使用真实交易日历确定目标日，目标日一旦确定就保存。保持原有停牌处理，缺失或停牌日不顺延成其他交易日。若政策以后改变，新增政策标识，新买入使用新政策，已有交易继续使用自身政策。
- 原 entry_price 与计价依据保持；复权用于把持有日价格转换到可比尺度。复用当前已验证的计算公式，保留使用的日线、复权凭据及来源证据。
- 新增规则版本本身无需加入结算器的选股版本白名单。新策略写入已支持的 settlement_policy 即可自动跟踪。未知结算政策属于显式错误，受影响记录保持可见。

### 2. 后台按未结算交易处理

把结算处理从当天选股扫描条件中提取为独立业务任务，复用现有业务调度进程及 PostgreSQL，不增加运行服务。

1. 每五分钟检查已买入且尚无最终结算的记录，覆盖所有选股规则和所有买入日期。新信号停用、候选为空、规则切换均不影响这一步。
2. 输入使用基础数据层已经发布的交易日历、日线、停牌事实和复权凭据。按交易及日线修订标识跳过输入未变的工作；以 200 笔为批次批量读取相关证券与日期，复用已有批量核验。
3. 未到期的记录更新已到日期的累计收益。到期且原政策要求的数据齐备时生成完整结算。数据不足显示具体日期、字段与原因，后续基础数据独立补齐后再次处理。
4. 该任务只写交易结果，不调用行情来源或触发补采。页面只查询已发布的交易进度和结算结果。
5. 继续使用既有交易锁，锁内复核交易仍未结算，最终结果单事务写入。重复执行、并发任务和进程重启只得到同一份已完成结算。
6. 原日线扫描、数据维护与回填入口统一调用该业务能力，消除仅当前规则结算的入口。生产部署后的补结算使用同一处理器。

### 3. 结算结果与历史读取

在现有交易表增加可空 JSONB 字段 `settlement_policy` 和 `settlement`，保持加法迁移。旧 `swing_signal_outcome` 增加同名字段以保存原政策及终态。现有 `outcome` 或旧表收益字段用作持有期进度及旧接口兼容结果。

- `settlement` 包含交易身份、结算政策、T+1—T+5 的真实日期和可比价格、累计收益、T+5 收益、胜负、有效结算日、实际完成时间及数据依据。
- 正常写入仅允许从空值变为完整结算。提交后历史接口与统计直接读取结算内容，发布新选股规则和基础行情后续修订不自动覆盖它。
- 基础数据确实发生错误、需要更正已结算结果时，作为明确的纠错操作单独处理，保留更正前结果与原因；本 Change 不增加通用人工改账界面。
- 历史观察日只展示截至该日的进度；观察日早于该笔有效结算日时，不展示最终结果或计入胜率。补齐后形成的历史结果标注实际完成时间，避免冒充当时已经得到的结论。
- 同一股票在不同日期的真实入账按 trade_id 各自跟踪。多路径按原入账主导路径统计，同一交易计一次。

### 4. 页面、查询与统计

模拟跟踪默认覆盖所有已入账交易，选股规则成为可选筛选项。

| 页面区域 | 查询范围与行为 |
| --- | --- |
| 跟踪中 | 全部尚未结算交易，包含早于最近五个交易日的待补数记录，分页展示 |
| 最近买入 | 最近五个真实买入交易日，跨规则，批次数和总笔数覆盖完整集合 |
| 已结算 | 已完成交易，按结算日倒序分页，能够进入全部历史 |
| 完整历史 | 所选买入日期、股票、路径、状态的全部交易，规则筛选默认全部 |
| 统计 | 与查询筛选同一集合，显示总买入、跟踪中、待数据、已结算、盈利、亏损、持平和胜率 |

每笔展示买入日期与价格、入账评分、交易路径、原规则、逐日收益、状态、结算日和数据缺口。原规则放在详情或筛选中，不要求用户先选对版本才能找到交易。详情从交易记录读取买入证据，不依赖最近候选缓存。

默认胜率按所选集合的已结算交易计算，盈利数除以已结算数，持平计入分母，未结算不计入分母。同一结算政策下可合并不同选股版本，另提供按路径、买入批次、选股规则分组比较。将来出现不同持有期或收益口径的政策时，统计按政策明确分组。首日盈利比例单独标明 T+1、已覆盖笔数和总笔数。

### 5. 跨仓接口与兼容

Provider 在既有 history/stats 路由增加显式 `investment-dashboard-swing-history-v4` 和 `investment-dashboard-swing-stats-v4`。

- 默认跨规则；`rules_version` 仅为可选过滤，返回每笔自己的 rules_version 和 settlement_policy_id。顶层使用 scope 与 rules_versions 描述集合，不以当前版本冒充全体版本。
- 支持买入日期范围、观察截止日、股票、路径、状态、规则、结算政策及分页。统一排序为买入日期倒序加 trade_id，所有筛选在分页前执行。
- `scope=open` 覆盖全部未结算交易，`scope=recent_buys` 为最近五个买入交易日，`scope=settled` 为已结算，`scope=all` 为完整历史。总数与分组统计基于完整筛选集合。
- v2/v3 保留单规则结构与默认范围，明确查询旧规则仍可用；同一正式交易的已结算收益统一读取保存结果。v4 联合两类已成交来源后统一筛选、排序和分页，按原结算政策提供可比统计。
- Dashboard 接入 v4 并同步类型、适配校验、页面和查询缓存。缓存身份包含实际筛选范围及交易结果修订标识。页面不得以当前选股版本覆盖用户的“全部规则”范围。

### 6. 现有历史记录接入

对账覆盖全部具有真实模拟买入凭据的记录。当前已核实的正式账本 549 笔全部覆盖，更早参考账本依据原成交字段分类接入，其已成交数量尚未在本轮生产核实。

1. 用已有入账证据和对应历史实现，为原交易补充结算政策，保持 trade_id、entry_price、日期、路径、评分及理由。v5.2.0、v5.3.x、v5.4.0 和已定义的 v6 正式账本复用已存在的五日收盘收益公式，记录各自原入场计价依据。
2. 已保存完整结算的交易，将原 outcome 的五日结果按字段一致性验证后登记为历史结算，注明 legacy_outcome 来源和登记时间。无需为迁移重跑这些已完成交易的行情计算。
3. 未结算但已到期且有有效数据的交易，由统一处理器补结算。未到期和确有数据缺口的交易持续跟踪。
4. 原记录缺少政策映射依据或完整结算字段时，保留原记录、原 outcome 并显示具体待核对原因，不从当前选股结果拼造旧交易。
5. v5.1.0 旧记录以原 entry_price、entry_time、entry_source 且 untradeable=false 确认已经发生参考成交，统一显示并持续结算；仅信号或 untradeable 记录保留为原历史信号。沿用 `swing_outcomes.settle_event` 的原收益和完成判据，拆出接受固定入场信息的结果计算，后续不再重新推定成交价或重过选股条件。原次日开盘与分钟 VWAP 入场、原 5/10 日收益按独立政策归组，使用原信号日期与实际入场日期各自定义。已保存终态直接迁移，不强行改成当前五日收盘政策。原表继续留存，统一接口通过来源身份去重。
6. 提供幂等的迁移命令，默认 dry-run 输出各版本/日期的交易数量、已结算迁移数量、可补结算数量和缺口。正式执行沿用同一身份对账，重复执行不新增交易、不重复结算。

### 7. 验收标准

| 场景 | 必须满足的业务结果 |
| --- | --- |
| v5.3.1 买入后切到 v5.4.0，再切到另一个新选股版本 | 旧交易始终显示，原买入事实一致，到期照常结算 |
| 新版本复用已支持结算政策 | 结算器无需增加该选股版本白名单 |
| 当前选股关闭或本日无候选 | 旧交易仍按日推进并结算 |
| 老版本各买入日期、早于五日窗口的未结算记录 | 全部可查；分组、分页、详情与总数一致 |
| 买入后跌出候选池、评分变化或结构失效 | 原交易持续跟踪，原入场事实可核对 |
| 200 笔批次中部分缺日线、复权凭据或停牌 | 完整交易正常结算，缺数逐笔显示，补齐自动完成 |
| 进程中断、并发和重复调度 | 无重复交易和重复结算，无部分写入 |
| 已结算后切规则、刷新页面或重跑任务 | 保存结果和胜率完全一致 |
| 新基础行情修订与历史观察日 | 已结算内容保持；历史查询不泄漏截止日之后结果 |
| 原始买入价与官方昨收不同、发生除权除息 | 基准仍为账本 entry_price，按原政策完成同口径换算 |
| 旧客户端与新接口 | v2/v3 原范围可用，v4 全规则范围可用 |
| 数据保护和运行开销 | 原交易数量及入场字段逐笔一致；批量读取无逐股 N+1；历史读取无行情计算、来源请求或业务写入 |

本地演示提供两次规则切换前后的跟踪列表、同一笔旧交易的入账与结算、跨规则历史分页和对应胜率。使用合成数据及已获授权的脱敏只读证据，所有写入仅在隔离测试库执行。

## Release Impact and Rollback

按用户后续授权随候选表列序调整一起发布。

正式发布时先 Provider 加法表结构、统一结算和兼容接口，再完成历史接入对账，随后 Dashboard 使用 v4。迁移命令与结算任务使用同一交易锁和条件写入，部署期间新入账记录也包含完整政策。页面切换前核对原入账数量、金额、日期及已结算结果。

回滚代码保留新增字段、所有入场事实和已落库结果，旧代码不识别新增 settlement 字段也不会删除它。旧程序回滚后仍有原跨规则结算缺陷，必须在回滚说明中明确，恢复服务与修复业务完成度分别核对。数据纠错使用明确的独立操作。
