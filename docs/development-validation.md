# 开发验证与简短部署

适用于三个业务仓库与平台工具。目标是提高功能首次提交的通过率、减少生产问题，同时保持部署简短。
复用现有 unittest/pytest、Vitest、PostgreSQL、构建与 CI；不新增测试平台、人工审批或统一覆盖率指标。

## 开发完成前验证什么

| 改动 | 必要验证与验收结果 |
| --- | --- |
| 功能、业务规则、缺陷修复 | 对照需求验证结果、状态和关键边界；覆盖与改动有关的缺失、陈旧、失败等场景。修复可复现缺陷时保留能暴露原问题的回归测试。不能只断言 HTTP 200 或没有异常。 |
| API、数据库、Provider/Consumer、投影或任务链路 | 验证受影响的真实边界：隔离 PostgreSQL 的读写/迁移、HTTP 鉴权/契约或关键链路；覆盖部分失败与恢复。外部来源、LLM 和通知用替身隔离；替身测试不称为真实来源验证。 |
| 查询、批处理、采集、调度、并发或明确性能目标 | 在提交前完成针对性的性能验证：代表性数据规模、耗时/吞吐/查询次数、必要的队列延迟或资源占用，并同时核对结果正确性。复用已有预算；没有预算时根据需求和当前基线确定合理目标。 |
| 页面、表单、交互 | 运行相关逻辑测试和构建，检查实际用户操作与关键状态。复杂交互保留必要人工检查或小范围稳定 E2E。 |
| 简单文案、样式、文档 | 检查实际受影响页面/构建或文档 diff、链接、命令；无需为此跑数据库、压测或浏览器全套。 |

一个 Change 只运行与实际改动有关的项目，不要求每个小改动都跑所有种类。
性能测试可以是既有测试中的查询次数、批次数或有界资源回归；涉及吞吐/延迟承诺时还需测量对应指标。
仅用小样本或 mock 的测试不能证明全量数据规模或生产吞吐。开发/CI 环境与 NAS 差异明确记录，
不把两者的绝对耗时直接等同；确需 NAS 专项验证时在本 Change 说明范围，不扩展为所有发布的门禁。

## 一次记录，自动复用

开始实现时将需求转成少量可核对的验收结果，随改动选择已有测试或补关键回归。
提交前完成受影响的本地检查；PR/main CI 自动验证合并结果。关键失败修复后再提交，失败只重跑
受影响检查。合并冲突、代码/配置变化或新失败使相关证据失效时才补验，不反复全量重测。

结果直接写现有 Change/PR 的 Tests：测试命令或 CI 链接、验证的行为与数据规模、结果及真实限制。
不另建功能/集成/性能三份报告，不要求测试数量、覆盖率或截图达标。必需测试因缺少环境未运行时
明确说明尚未验收的边界，不能把计划执行、跳过或 mock 结果写成实际通过。

stock-analyzer 已有 pytest/PostgreSQL 回归，Dashboard 已有后端/迁移/前端/构建 CI；
marketNewsFeed 的离线 CI 复用 `scripts/test_offline.py`，包含配置、功能、PostgreSQL 和已有查询成本回归。
新增 CI 文件只有在合并且实际运行后才成为自动执行证据；不因文档更新宣称过去所有功能均已充分测试。

## 发布只做切换与短检查

复用冻结 main SHA 的 CI、候选与开发验证，调用一次部署入口，完成精确镜像切换、运行身份、健康
和一次既有 smoke；保留上一稳定镜像与实际需要的备份。普通部署不额外执行完整功能/集成/性能套件。
新计划不填写六项手工 gates；CI/镜像/权限/漂移/必要备份/健康等实际检查仍由发布器执行。

普通部署不等待所有采集周期结束、队列清空或全量行情补齐。数据追平状态可单独报告；核心功能
失败、错误结果或本次明确要求的验收目标未达到仍要处理，不能把已知缺陷归为非阻塞观察。
如果只完成部署 smoke，应报告其范围；不能据此宣称做过真实来源、性能或全链路验收。

不重复 preflight/prefetch/verify、恢复/回滚演练或浏览器巡检。部署完成先报告可用结果，记录集中
收尾，清理不阻塞。正式发布授权、精确版本和数据保护边界见 [发布规则](../RELEASE_RULES.md)。
