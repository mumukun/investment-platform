# 基础数据采集与业务功能解耦方案

- Change：CHG-20261027-002。
- 日期：2026-10-27，Asia/Shanghai。
- 状态：APPROVED / IN_PROGRESS；用户已确认方向并授权本地重构和验证，不授权生产发布。
- 依据：用户最新原则优先于此前草案：数据采集独立运行；业务功能不干扰采集；业务派生数据与基础数据解耦。
- 配套：[现有入口、库表与归属清单](CHG-20261027-002-data-ownership-inventory.md)。

## 1. 结论与约束

推荐在 stock-analyzer 同一仓库、同一 PostgreSQL 内，增加独立的 stock-data 采集运行单元。复用现有镜像，在 Compose 中作为第三个服务运行；stock-watch 运行业务计算/监控，stock-api 提供查询。没有新的 HTTP 服务、仓库、数据库、数据商、消息队列或 Redis。

独立容器是为了让采集拥有独立启动、停止、重启与健康检查。采集程序不作为某个业务任务的子进程，也不依赖业务模块维护自己的调度。

只有三条数据流：

1. 来源 → 采集程序 → 基础数据表。
2. 基础数据表 → 业务计算 → 业务结果表。
3. 基础数据/业务结果 → API → Dashboard 或其他消费者。

业务不能反向触发采集、补数、提高采集频率或修改基础数据。页面刷新、候选产生、自选新增和引擎开关均不改变数据计划。数据缺失时按现有规则等待、降级或说明覆盖范围，不让业务临时接管采集。

这会涉及 stock-analyzer 至少 30 个代码、测试、文档文件，新增一个 Compose 服务。Dashboard 的采集触发按钮/文案与兼容模型按真实影响修改；marketNewsFeed 只验证可选股票查询兼容，不改新闻业务。历史清理继续搁置。

已确认的问题：

- stock_data.py 已统一部分供应商调用，但 watch、短线、波段、科技/轮动、历史补数仍独立发请求、安排时机和写公共表。
- intraday_stock_bar 有多个写入实现。短线快照的 open/volume/vwap 空值与波段完整报价可能相互覆盖，这是代码风险，未声称观察到某次生产覆盖。
- 该分钟表包含按分钟采样的当日累计行情，也混有回填五分钟 K 线；两者语义不同，不能统一后直接当一分钟 K 线使用。
- candidate_history、short_tracking、hotmap_data、图表后台 refresh builder、公司资料/席位等查询有隐式采集或补数路径，不能只迁移显眼的定时任务。
- tech_board_fact 被科技、轮动、概念共用，并混有基础事实与研究运行记录；按页面名决定所有权会遗漏公共依赖。
- legacy live=true 和 watchlist refresh_quotes=true 会触发来源请求；板块成员 refresh POST 会让 API BackgroundTasks 执行采集。它们与用户最新原则冲突，必须取消其控制采集的能力。

此前 2026-10-27 生产只读统计：intraday_stock_bar 约 1,409 万行、3.78 GiB；tech_board_fact 约 219 万行、3.34 GiB；swing_daily_bar 约 97 万行、315 MiB。行数为 PG 估计值，大小含索引，不是本方案实施后的容量。tech_board_fact 抽样约 99.49% 为 quote。Dashboard snapshots 约 3.98 GiB，属于业务投影，不能迁入采集程序解决。

## 3. 最终架构与所有权

```text
获准数据来源
     |
     v
stock-data：独立目录、采集计划、来源适配、校验、事实写入
     |
     v
PostgreSQL：基础事实 + 采集状态
     |
     +-----------------+------------------+
     v                 v                  v
短线/波段计算        自选/监控          板块/研究/报表
     |                 |                  |
     v                 v                  v
各功能自己的结果、画像、状态、信号与证据表
     |                 |                  |
     +-----------------+------------------+
                       v
                 stock-api 查询
                       v
           Dashboard 后台投影 / 可选新闻查询
```

业务到采集程序没有调用箭头。数据程序也不读取候选、策略分数、关注级别、业务结果或页面访问记录来决定工作。

| 层 | 负责 | 禁止 |
| --- | --- | --- |
| 采集 | 数据目录、计划、来源调用、真实日期/单位/完整性校验、基础事实、采集状态、受控运维补数 | 调用策略、按候选池或关注等级安排采集、写业务结果 |
| 基础数据仓储 | 统一身份、口径与来源，提供无网络/无隐式写入的批量读取 | 缺失时自行调用来源或修改事实 |
| 业务计算 | 只读基础数据，执行自己的规则，写自己的结果/证据 | 抓数据、补数、修改基础事实、改变采集计划 |
| API/页面 | 读基础事实或业务结果，显示实际日期/覆盖/状态；维护业务主数据 | 页面刷新触发采集；把投影检查时间当行情时间 |
| 运维 | 单独管理数据目录/计划，执行数据程序自己的补数命令 | 将运维入口包装成业务计算/页面的自动备用 |

所谓解耦不等于复制基础数据。业务可以保存某次决策所用证据，必须记录输入版本/日期；证据不能成为反向更新公共价格的依据。业务规则变更只重算业务结果，基础事实不变。

## 4. 独立采集目录与计划

### 4.1 范围由数据域定义

- A 股：按有效证券主数据目录维护全市场；上市、停牌、退市等按真实资料处理，不读取自选/候选池决定是否维护。
- 指数、ETF、港股、海外资产：使用独立数据目录，迁入已有获准资产和口径；保留指数编制、交易所、价格/净值、单位、市场时区。目录由数据维护职责管理，业务只查询覆盖情况。
- 行业/概念成员：它们本身是基础资料，由数据程序维护；不能由板块页面打开或策略筛选结果触发。
- 日历、交易规则、分类、资金、融资融券、已授权席位事实：依各自数据计划采集。
- 新业务使用目录外资产/历史范围时返回明确的覆盖不足；需要扩充时作为独立数据维护变更处理，不由业务代码暗中注册需求。

现有业务所用证券仅作为迁移时的一次性覆盖核对，不把运行时业务池作为新目录来源。不复制用户笔记、关注理由等个人数据到采集配置。

### 4.2 首版数据计划

固定能力计划放在数据模块内，默认值随代码提供；不引入通用调度 DSL 或用户配置平台。现有纯数据频率迁入数据域设置；SWING_ENGINE_ENABLED、SHORT_SELECTION_ENGINE_ENABLED、自选关注级别等不再控制它。

| 数据集 | 首版计划 | 范围/约束 |
| --- | --- | --- |
| A 股最新报价 | 交易时段每 60 秒一轮，原 45 秒轮次预算，最多 4 个并发任务 | 全有效证券目录；已成功小批立即提交，未完成范围轮转恢复，不等整轮发布 |
| 全市场快照 | 原每 5 分钟，09:35～14:55，16:05 终场 | 独立于热力/短线功能开关 |
| 累计行情分钟采样 | 真实源时点落在相应交易分钟时，每证券每分钟最多一个有效样本 | 全市场固定口径，不因某股入选/自选才记录；不是一分钟 K 线 |
| 原价/前复权日线 | 原 15:30、17:30、20:30 维护和 15 分钟恢复窗口 | 全证券所需最近 120 个交易日及计算窗口前置点；历史缺口轮转，现有更长历史保留 |
| 真实五分钟 K 线历史 | 每日 15:10 起至下一开盘前，按完整交易日差异维护最近 20 个交易日 | 全证券目录，初次逐批建立覆盖，沿用 2 并发；来源只能返回有限历史时明确缺口，不由候选池临时触发 |
| 证券主数据/分类/成员/日历/规则 | 搬迁原盘前/盘后日程及其有效重试 | 新股在数据目录更新后自然进入采集，不等业务选中 |
| 板块、指数、ETF、港股等 | 保留既有约 60 秒活跃期/900 秒非活跃期及概念约 120 秒维护规则 | 范围改为数据目录，依各自市场日历，不统一套 A 股时段 |
| 行业资金 | 保留来源分钟时钟、完整 48 行业原子批次及历史维护 | 不因图表或行业筛选改变采集范围 |
| 海外、融资融券、席位等 | 原已启用数据能力的有效日程/窗口；原低频目录按来源日期更新 | 不扩大账号/用途；不自动启用原来关闭的海外来源 |

在同一数据程序内，来源能力/资产/口径相同的采集单元去重；这是数据程序内部安排，不接受功能模块提交请求。快照日期核验确需个股报价时复用该轮符合校验要求的已采集报价，不用服务器接收日冒充市场日。

采集范围独立会比现有“只有候选才保存一分钟/五分钟历史”更完整，不能宣称数据量一定下降。以约 5,224 只、240 个分钟估算，累计采样上限约 125 万行/交易日；按旧表大小/估计行数折算约 288 字节/行，约 344 MiB/日、20 日约 6.7 GiB，尚未包含新元数据、WAL、真实 K 线和运行开销。只是容量量级，不是实测承诺。本轮不启动历史清理；上线前必须按已选数据范围核实可用磁盘和增量写入预算，不足时先调整独立数据集计划，不能改回依业务池采集。

## 5. 运行、故障与单一写入者

- Compose 新增 stock-data，复用同一精确镜像，入口 scripts/market_data_worker.py；不暴露新端口。stock-watch 不启动、停止或监督采集进程。
- Docker 保持其独立运行和重启；数据进程自己的固定调度循环执行计划。业务只重算/重启、引擎关闭、页面无人访问时，采集继续。
- 数据进程用 PG session advisory lock 保证单一所有者，网络任务有界并发；事实和状态通过短事务原子提交。持锁连接失效后停止提交结果，重新持锁才恢复，不在网络请求期间占用长事务。
- 实时任务与慢历史任务分别排队；历史故障不阻塞最新行情；失败沿用适配器有界重试，不再叠加业务重试或代理备用。
- 采集状态中每 15 秒更新 collector heartbeat。健康检查只判断程序/DB 可用及心跳；来源暂时无数据记录为能力降级，不通过容器重启循环假装恢复。
- 采集状态查询只读；运维补数必须使用独立数据 CLI，参与同一锁协议。没有待业务请求队列，也没有业务调用的刷新 API。
- 共享 NAS/PG 的物理资源竞争仍存在，不能承诺绝对性能隔离；通过独立运行单元、短事务、有界并发和压测控制，不把业务锁持有到采集写入中。

新增命令在实施后提供：常驻 market_data_worker.py、--once --dataset、--status、--health、--once --dry-run；dry-run 只读计划/缺口，不联网、不写库。--status/--health 不初始化表。既有补数 CLI 保留运维用途，但不被业务/API/投影任务调用。

- 候选、信号、状态、画像、模拟交易、研究运行、复盘证据继续由业务层保存；不回写基础事实。

### 6.3 时间、口径与一致性

1. 实际 source_time、received_at、checked_at 分开；日期型事实只有真实日期时不补造秒级时间，旧资料缺失来源时保持未知。
2. 同源时点同内容不改事实；价格相同但有新有效源时点仍是新观察，不能把静止价格误判为采集停止。
3. 旧/乱序报价不能覆盖新报价。同分钟完整报价与缺字段快照冲突时保护可验证完整记录；不同来源/时点的价格与量额不能悄悄拼成“完整报价”。
4. 当前价从 latest 读取，量价指标用自身真实完整样本时间，避免旧累计量伪装成新报价。累计采样与真实 K 线模型不同，不暗改算法口径。
5. 小批事实与对应版本/ready 同事务发布。内部状态为 collecting、ready、partial、stale、unavailable；数据 ready 不等于业务结果已重算。
6. 统一身份使用市场/资产类型/交易所/原生代码，保留原 security_id、sh/hk、cni-* 外部 ID 映射；股票与指数不因类似代码而合并。保留来源原涨幅及 ratio/percent 单位的审计信息。
7. 每次计算通过只读事务固定已提交输入，结果记录输入日期/版本/received_at。截止后才收到的数据不能倒填为截止前已知；历史查询不读未来事实。
8. local_db 增加不执行 schema bootstrap 的显式只读连接；reader、status、dry-run 不隐式 DDL/补数，未初始化时明确不可用。
9. 新事实变化触发业务下一轮计算；交易日、截止时间和状态到期仍由业务时钟驱动。不能在行情不动时停止正式结果/状态推进。
10. 保留 CHG-20261026-006 的最近可用评估展示：标注年龄与实际日期，新事实改变资格再更新；不新增统一陈旧阈值清空列表。参与门禁与列表可见性继续分开。

## 7. 历史与前复权

原始价通常稳定，前复权历史可能因除权除息、拆分和来源修订变化。前复权序列仍从获准第三方接口取得，不凭数据库某天价格自行推算全套历史。

保留已有本地优化：按实际窗口请求、未变事实不写、50 只批次、同源完整日期集合校验、真实修订前后值审计、缺失原价/成交量不覆盖已有值。核验证据与价格行分离，正常重复核验不把历史所有 adjustment_as_of 改为今天。

腾讯当前适配缺少能独立证明完整复权序列版本的因子/版本号，仍需下载必要完整核验窗口；Sina SDK 可能内部全量下载后裁窗。不能宣称已经做到每天网络只取一条。该工作完全由数据程序执行，业务不会因缺日线而另发请求。

历史更正只更新基础事实/版本，由业务自行决定依其重放政策重算结果；采集程序不能直接改业务分数/历史结论。已发布决策证据保留当时输入，避免新复权序列悄悄改写旧结论。

## 8. 来源、既有规则和接口行为

- 个股默认仅腾讯/新浪；国内请求 DIRECT；没有新增 API key、账号或收费依赖。已配置的可选海外账号继续原有启用边界，不为重构要求补凭据。
- 东财/同花顺仅保留已授权具体用途，不能把现有代码搬进 worker 就视为放行；指数编制、行业分类、资金、ETF价格/净值不跨口径拼接。
- fetch_industry 旧实现指向东财 F10，通用传输层已拒绝，该用途未获恢复授权。只保留已有真实资料；无获准替代时明确缺失，不能拿其他分类冒充 EM2016。
- stock-analyzer ADR 0002 的旧执行方案“不引入新服务”与本方案增加独立 stock-data 运行单元不同。建议用户确认后补充 ADR，明确采用独立采集 worker 容器，保留同仓/同库/无新 HTTP 服务；本轮不静默改旧决策或部署。
- Dashboard ADR 0019/0022 的 API 消费、独立库、后台投影与页面只读继续执行；不删除必要后台投影，不读上游 PG。

旧控制采集的参数和命令不能保留原控制权，否则原则落空：

| 现有行为 | 最终行为与兼容处理 |
| --- | --- |
| live=true | 保留查询路径和原 live_quote 价格/涨幅/换手/日期字段，改为附带已采集最新行情；提供实际源时点/陈旧状态，不即时采集。无可用事实仍返回原错误信息字段，不伪装成功 |
| watchlist refresh_quotes=true | 不再抓取/写基础数据，只读公共最新行情供业务投影；响应不能声称采集已完成，persisted 仅描述本功能投影而非基础事实。Dashboard 现有客户端已传 false |
| 图表缺口/历史查询 | 返回已覆盖部分或现有不可用状态，说明覆盖与日期；不登记采集需求，不启动后台补数，等独立数据计划推进 |
| 板块成员 refresh POST 202 | 先迁移 Dashboard 为“重新读取”已有结果，不再发采集命令；旧命令进入弃用并在后续收口版本明确返回不再支持，而非假返回202 |
| 公司资料/席位等按需查询 | 只读数据目录已覆盖的资料/明细，实际无数据与采集失败分别说明；不通过查询等待采集或临时拉源 |
| add/update/remove 自选 | 只维护业务主数据、读取基础数据和重算自身投影；不变更基础目录/采集计划 |

这里存在真实的行为不兼容，不能把“字段没改”就称为兼容。实施采用 Expand→Migrate→Contract：先增加独立事实/状态及纯读取能力，迁移实际调用方，再在后续收口版本移除旧采集控制语义。旧接口/字段不与替代接口在同一发布中同时增加和删除；收口行为变更按 MAJOR 评估，并明确契约版本/弃用错误。过渡期未移交的旧行为如实记录，不能提前宣称完全解耦。

新纯读取接口固定为 GET /api/market-data/v1/status 与 GET /api/market-data/v1/quotes，Bearer 鉴权；quotes 接受已规范化 instrument_ids，批量上限 100，返回 contract_version=market-data-quotes-v1、实际日期/时间/质量/覆盖及 items。status 返回 contract_version=market-data-status-v1。两者无刷新参数。已有分析/图表读取接口保持；需要新版本的旧命令语义单独记录。新闻报告保留原查询字段与 8 秒边界，读取已采集价格；其核心采集不参与改造。

## 9. 五个可独立交付阶段

每阶段停在这里系统也能使用。未迁移域继续标为旧路径；每个域切换时必须同时移交来源执行、事实写入与调度，避免双生产者。

### 一：基础仓储与统一写入

纳入已验证日线优化；建立基础状态/latest/区间K线/辅助事实与业务结果表的增量结构；统一现有公共写入实现，修复空字段冲突，添加只读仓储。新旧数据兼容读取，不批量重写历史。先新增纯读取能力，旧调用方不受影响。

### 二：独立数据程序与核心行情

增加 stock-data Compose 服务和独立目录/计划，移交全市场快照、全市场报价与累计采样。watch、短线预选/跟踪、波段运行/发现改读仓储，只写自身结果。旧对应网络调度同一变更中停止；关闭引擎不影响数据。数据程序不 import 业务池、watchlist 或策略模块。

### 三：历史、主数据与隐藏补数

移交日线、真实五分钟历史、证券分类、日历、规则；停用 candidate_history、short_tracking、hotmap_data、图表 refresh builder 等业务补数路径。图表历史范围由数据计划决定，缺口不会反向发请求。新目录范围与容量在隔离环境验证，不用生产批量回填验证开发。

### 四：板块/专用事实与业务结果分离

移交科技/轮动/概念成员及报价/日线，市场结构/ETF、行业资金、海外、融资融券和已授权席位来源执行。公共事实归数据程序，排名/研究/案例/运行证据归业务。混合表按基础 kind 与派生 kind 迁读写，旧数据保留。成员采集按钮改为读取状态/结果，业务不能修改数据目录。

### 五：契约收口与全链路验收

按弃用顺序完成 legacy live/refresh、成员刷新和资料查询的纯读取语义，明确破坏性版本影响；跨仓兼容/界面迁移先完成再停旧控制流。核销所有 HTTP/SDK/后台/CLI 隐式入口，最终业务到采集的控制路径为 0。同步运维、目录、来源、表功能索引、ADR、契约与证据。不做历史清理或删除旧表。

预计约 9～14 个工程工作日：仓储/一致性 1～2、独立程序/核心迁移 2～3、历史/主数据 2～3、板块/专用域 3～5、契约收口约 1。是工作量估计，不是承诺；实际拆分根据影响核对，不能为了赶时间保留隐式采集。

## 12. 回退、风险与发布边界

最关键的假设是现有获准来源能够在预算内维护选定的独立数据范围。免费来源吞吐/历史覆盖不足时，数据程序公布 partial/覆盖缺口、按自己的计划恢复；业务继续使用最近可信事实。不得让业务临时抓取、减弱门禁或放行未授权来源。

范围从候选池扩至固定全市场带来的网络/容量成本是真实取舍；已有全市场分钟预选网络可复用，但全市场完整采样/真实K线的持久化可能增长。上线前必须核实；历史清理不作为本轮隐含动作，也不因数据增长偷偷删旧数据。10倍范围首先受限于来源吞吐与历史写入，不能靠无限线程解决。

所有迁移是 Add→验证→切读写，旧表/字段/历史保留；大表不做默认全量回填。切换前按仓库规则验证备份。每阶段保留上一个验证过的精确镜像/Commit，回退时统一切回对应股票运行单元，防止双采集者。新表保留不降级；新真实K线若旧代码不认识，可通过独立运维程序从已保存事实补原兼容表缺失，不能由业务自动补。旧日线代码不认识独立核验证据时可能需要其原有核验恢复旧时间戳门禁，不能承诺仅换镜像无条件恢复。

数据状态就绪与业务结果就绪分开发布。基础事实修订不直接重写业务历史证据。共享表存量混合/未知来源行保留可见兼容状态，不能在迁移中造来源与日期。

方案确认只进入本地重构与必要测试；Commit、Push、PR、Merge、MAJOR版本/Tag、生产部署和数据清理仍需各自授权。正式发布先兼容扩展、再Consumer迁移、后契约收口，不以本方案代替发布授权。
